# 深渊行者：美术、画风与游戏界面整改任务书

> **2026-09-29 更新：用户已明确偏好色彩更浓厚的卡通画风，类似《魔兽世界》。本文此前的低饱和方向已被替代，实施以 [最终可执行文档](../art-independent-20260929/fix-request.md) 为准。本文保留作历史方案记录，不再作为色板与画风的实施依据。

2026-09-29｜视觉验收结论：**未通过**｜以下为建议方案，尚未实施。

本轮优先解决“画面像可玩的游戏原型，尚没有统一的游戏美术表现”这一问题。成长闭环和数据库测试作为功能证据保留，不能作为美术、画风与游戏 UI 达标的依据。

## 一、实际画面的问题

1. **世界空间主要是几何占位。** `scene.ts/drawChunk` 用交替色菱形绘制地面，树木、建筑、门与桥大量采用椭圆、三角形和矩形。道路和自然地形的边缘缺乏过渡；画面看起来像测试场，而不是值得探索的地方。
2. **画面中的美术语言不统一。** 角色是有描边与体积的偏 Q 版二维动画；场景是简单块面；系统入口偏单色工具图标；技能图标高饱和；大面板使用灰银金属边框。每部分都能辨认，但组合后缺少共同材质、光照和笔触。
3. **HUD 像多个信息盒子。** 生命、目标、模式、小地图与系统入口都被较重边框包住，视觉权重接近。战斗动作与地图没有成为唯一主角。
4. **面板缺少游戏物件的质感与秩序。** 标题栏空白，厚边框和拉伸装饰明显；道具格子抢眼，物品轮廓和角色装配关系反而较弱。
5. **素材接入不完整。** `gear-bow.png` 与 `skill-lance.png` 已在实际资源目录，但 `packages/asset-manifest/ui.json` 没有 `gear.bow` 与 `skills.lance`，导致文字回退。应先修复清单映射，不能把这些条目当成没有资源而重做。
6. **动作与效果没有形成割草观感。** 飞行物、区域、护盾多是简单圆点与轮廓，缺少前摇、释放、命中、消散的统一表现语言。颜色变化和伤害数字不足以承担全部打击反馈。

证据：[最新野外画面](final/field.png)、[最新背包画面](final/preview-race.png)、[最新分解确认](final/salvage.png)。

## 二、确定一个贯穿全游戏的美术方向

建议方向：**手绘二维奇幻 ARPG，偏 Q 版角色、低饱和自然环境、古铜与符文 UI。** 与现有角色的比例和左右朝向匹配，保持二维斜视角地形与脚底定位。

画面应让玩家感受到：在风化遗迹与林地中远行，角色与魔法鲜明，环境安静但有危险；割草时动作与敌群变化清晰。

### 统一规则

- **造型：** 角色保留清楚的外轮廓、较大的头部与武器；环境使用略简化的手绘体块。建筑、岩石、树冠都有厚度、顶部与接地关系。
- **笔触：** 采用有限层次的明暗与柔和纹理；重要轮廓清晰，地面细节克制。材质复杂度服务于实际游戏显示尺寸。
- **光照：** 首个样板统一左上光源、柔软接地阴影与冷色暗部。先做一致的美术明暗，不新增复杂实时光照系统。
- **环境：** 低至中饱和、不过度明暗碎裂；道路与入口自然形成引导。
- **角色与掉落：** 比背景更清晰，有足够亮度差；武器、敌人类别与关键状态靠形状也能区分。
- **界面材质：** 深墨青底、细古铜边、少量符文与磨损。纹理集中在边缘与角部，文字区域保持干净。
- **特效：** 技能高亮集中在作用时点和主要轨迹；敌方危险形状优先，不能被玩家特效覆盖。

### 第一版视觉色板

这是初始样板色板，需要在组合场景里确认，不是整张画面只允许六种颜色。

| 用途 | 颜色 | 使用方式 |
|---|---|---|
| UI 底与冷暗部 | `#182724` 深墨青 | 面板底、描边、环境暗部基调 |
| UI 边与选中强调 | `#B79252` 旧古铜 | 细边、主要按钮、选中状态；不铺满所有边框 |
| 地形基调 | `#66775B` 林地绿 | 草地、树冠基调，配少量自然色变化 |
| 道路与石材暖部 | `#B3A181` 风化砂石 | 道路、遗迹受光面、主路引导 |
| 魔法与可交互反馈 | `#6AB7A4` 青玉 | 友方魔法、据点和交互强调 |
| 敌方危险 | `#D8624B` 朱砂 | 危险边界、受伤与警告；同时使用形状和动画 |

字体：先复用已导入的 Noto Sans SC 作为正文、数字和提示。只为标题制作一种有明确奇幻气质、字形可读的标题处理；字体或字标有许可依据。正文不能因为“像游戏”而使用难读的装饰字体。标题约 22–28 px、正文约 14–16 px、次要信息约 12–13 px作为 1280×720 起点，低高度布局另外处理。

## 三、逐模块整改

| 模块 | 具体处理 | 所用 skills | 达标依据 |
|---|---|---|---|
| 世界地面 | 替换棋盘式纯色菱形；制作草地、泥地、石路与混合边缘；道路含转角、分岔与破损变化 | `level-design`、`game-design-fundamentals` | 无调试网格观感；主路可辨；连续行走时无明显接缝与突变 |
| 植被、建筑、遗迹 | 用真实可拼装素材建立体块与接地阴影；统一斜视角和光照；区分可通行装饰与实际阻挡 | `level-design` | 树、墙、门、房屋能从轮廓识别；遮挡、碰撞与显示位置一致 |
| 场景构图 | 做营地出口、战斗空地、遗迹入口三类构图；近景边缘、中景战斗、远处地标建立层次 | `level-design` | 不看任务列表也能感知道路与入口；有整理空间和战斗空间 |
| 角色与敌人 | 首批选一个风格一致的角色和四类敌人；统一描边、色温、显示比例、脚底锚点与影子；精英通过轮廓/附属造型区分 | `game-design-fundamentals` | 角色不漂浮、不因换动画跳动；密集敌群中能找到玩家并分辨敌人类别 |
| 战斗特效 | 六个样板技能做释放、轨迹、命中、消散；友方与敌方用不同形状语言；限制累计亮度与覆盖面积 | `game-design-fundamentals` | 30 秒战斗中能看出范围斩击、远程、控制、护盾和治疗差别；危险圈始终可见 |
| 战斗 HUD | 顶左压缩为头像与两条状态；任务只保留一条主目标；底中技能栏；模式靠近技能栏；小地图与系统入口缩小并分层 | `frontend-design`、`ui-ux-pro-max` | 地图成为主体；不需要读多个信息盒子才能理解当前行动；主要操作不被遮挡 |
| 自动战斗表现 | 全自动显示小型活动范围和当前行为；停止时局部强调原因；模式切换有短反馈 | `interaction-patterns-components`、`frontend-design` | 能区分自动寻路、接敌、施法、拾取与停止；状态反馈和实际行为一致 |
| 背包与角色装配 | 左侧角色与四槽位，中间物品格，右侧比较；统一物品底板、品质与锁定标记；减少空格子的视觉权重 | `frontend-design`、`ui-ux-pro-max` | 第一眼能看懂角色穿什么、选中什么、换装改变什么；物品图标没有文字占位 |
| 技能构筑 | 当前装配成为主视觉；技能库分组并展示技能身份；把升级与装配操作在视觉上区分 | `frontend-design`、`interaction-patterns-components` | 当前构筑可一眼辨认；技能图标、颜色与实际效果统一；操作不是一屏等权卡片 |
| 地图与任务 | 使用同一符号体系表示据点、入口、敌群与首领；主目标、区域名、次要任务有明确层级 | `level-design`、`ui-ux-pro-max` | 小地图无越界；图例与世界实际标记一致；信息不用靠长句堆叠 |
| 首领与失败画面 | 首领入口具备独特地标；首领血条只在战斗时出现；失败保留场景背景与明确后续操作 | `frontend-design`、`interaction-patterns-components` | 首领有场景身份，失败有反馈和方向；不使用通用后台弹窗承担全部气氛 |
| 登录与加载 | 制作同画风的场景主视觉与游戏字标；账号表单融入画面边侧；加载展示当前区域与明确状态 | `frontend-design`、`ux-writing-content-design` | 从启动画面就能判断是二维奇幻动作游戏；登录、营地、野外像同一个作品 |
| 按钮、提示、确认框 | 同一边框与按钮套件，区分主操作、次操作、危险操作；所有状态及焦点有视觉规则 | `frontend-design`、`interaction-patterns-components`、`ux-writing-content-design` | 普通、悬停、按下、选中、禁用、焦点均一致且可辨；确认层与父面板有清楚层级 |

上述技能辅助设计与实现，不代替合格的游戏美术素材或实际视觉评审。涉及新栅格概念图与贴图时可使用 `imagegen`；整套角色动画、精确拼接地块和交互 UI 仍须切图、导出与实机组合验证。

## 四、资源怎么处理

### 1. 保留并筛选

先选现有角色中动作完整、比例一致的一组；现有可读的装备和技能素材按用途复用。不能仅按资源数量决定采用，也不能把风格相互冲突的素材全部放到同一场景。

建立清单：实际 ID、来源、许可、原尺寸、目标显示尺寸、动作、脚底锚点、光照方向、风格分组、用途、适配项、内容哈希。分为直接使用、需适配、需补充和本阶段不使用。

### 2. 先修映射再判断缺素材

修复 `gear.bow` 与 `skills.lance` 等缺项；内容构建检查所有正在使用的技能、装备和系统入口 ID。正式资源缺失应让资源构建失败，而不是在玩家页面静默显示 ID 或名字。

当前技能原图有大量 24×24 素材。若目标是在 48–56 px 技能按钮中保留清晰手绘细节，应先查找高分辨率原图；没有原图时按统一画风重绘或制作高分辨率替代，再按实际尺寸验收。放大和滤镜不等于获得新细节。

### 3. 新增环境素材

首批仅服务一个组合场景：草地、泥地、石路及过渡边缘；树木、岩石、断墙、石柱、门、灯；营地建筑与首领入口；地面影子、交互标记与掉落。

按美术方向选择一套具备斜视角和模块拼接能力、许可可用于发布的素材，或按同一规格制作。不得把多套风格不同的免费资源直接混用。整张背景只能用于远景或固定房间，不能代替世界地图。

### 4. 重做 UI 套件

从现有面板中提取可用细节；不合适的灰银金属条改为统一古铜与符文样式。提供独立的角、边、内容底与标题部件，明确九宫格不可拉伸边界。主/次/危险按钮与道具槽位分别制作，不共用一个重装饰框。

环境素材用图集；界面图标维持统一视觉尺寸和透明边距；系统图标采用同一绘制或描边规则。质量差异大的低分辨率来源必须记录替换任务。

## 五、落地位置与模块联动

- `apps/web/src/scene.ts`：替换 `drawChunk` 的纯色地形与几何装饰，接入环境图集与分层。保留现有世界坐标、导航数据和逻辑分块；外观升级不能改变命中、移动或实际作用范围。
- `packages/content/maps/`：记录美术图层、装饰摆放与必要锚点，维持碰撞、出生点、入口与区域连接的明确数据。美术改变位置时同步核查碰撞和交互。
- `packages/asset-manifest/` 与 `tools/build_assets.py`：建立完整 ID → 实际资源映射、尺寸、切片与图集记录；检查导出和正式包一致。
- `apps/web/src/presentation.ts`：调整 HUD 与面板结构；统一标题、图标、状态与焦点节点。美术切换不能破坏现有命令队列和正式资产来源。
- `apps/web/src/style.css`：集中管理字体、材质、色板、间距、尺寸与按钮状态；组件使用同一套规则，清除互相覆盖的旧样式。
- 表现消费模拟事件：施法、命中、状态、死亡和正式奖励确认分别驱动特效，不能通过动画结束发奖励。
- 服务端：继续持有正式资产、成本、奖励和进度。画风整改以客户端表现与内容资源为主，不要求为美术方案新增服务端战斗系统。

## 六、执行顺序：先统一一屏，再扩展全游戏

### V0：美术方向样板

交付一个风格板，包含角色、敌人、树石建筑、环境光照、六色基调、字体、面板、图标与效果示例。全部放到同一板上检查一致性。附来源与哪些资源实际可用，不以漂亮但无法落地的概念图冒充游戏资产。

### V1：一屏完整游戏视觉

只制作一段营地出口到遗迹空地的场景。包含：实际角色与敌人、地面过渡、道路、地标、遮挡物、技能、危险圈、掉落和完整 HUD。

交付同一机位的战前、战斗中、掉落三张 1280×720 实机截图及一段短录像；另交一张背包打开画面。先按玩家看到的整体效果评审，局部图标漂亮但整屏混乱不得通过。

### V2：界面套件与其他主要面板

将已经通过的样板规则扩展到背包、技能、地图、首领、设置、登录与提示。页面整体重组，不仅在旧布局上换背景颜色。

### V3：全资源一致性与分辨率验收

核查所有实际使用 ID、标题、资源加载、材质、按钮状态、角色比例、动画锚点和特效颜色。检查 1280×720、1600×900、1920×1080；如果继续支持 1024×576，另提供低高度布局或清楚的最小窗口限制。

## 七、真正的视觉通过标准

以下标准针对实机画面，不由单元测试数量代替。

1. 启动、野外、背包三张截图具有同一套造型、材质、色彩和字体语言。
2. 普通游戏视图没有调试棋盘、纯几何树房、素材 ID、文字图标占位和空标题。
3. 隐藏 HUD 后，世界本身仍有道路、场所、地标、层次与视觉吸引力。
4. 打开 HUD 后，第一视觉焦点仍是角色与战斗；玩家能迅速看到生命、主要技能、目标和模式。
5. 首个样板在敌群与特效同时出现时，角色、危险边界和掉落可辨认；减弱特效不会丢失战斗信息。
6. 场景边缘、树石、入口与碰撞相符；角色没有动画跳位、错误阴影和无规则遮挡。
7. 图标符合物品或技能的实际身份，正式使用的资源缺项为零；图标与角色的清晰度在实际显示尺寸协调。
8. 主要分辨率无面板越界、正文压在边框上、按钮遮挡和小地图溢出。
9. 用同一机位的前后对照确认整屏改善；邀请未参与开发的人看短录像，能指出主角、敌人、危险、入口与当前操作。记录结果，不能自行写成“玩家已理解”。
10. **视觉通过与功能通过分别签署。** 能通关、能结算、能保存，不足以证明美术与游戏界面合格。

## 八、可直接复制给开发者的总任务

> 本轮优先执行《美术、画风与游戏界面整改任务书》。将现有偏 Q 版二维角色、几何占位场景、灰银金属面板和多来源图标统一为手绘二维奇幻 ARPG：低饱和自然环境、鲜明角色、深墨青与古铜符文 UI。先完成资源映射与风格筛选，再制作一屏包含道路、地标、遮挡、敌群、技能、危险提示、掉落和 HUD 的真实游戏样板。样板整体视觉通过后，扩展背包、构筑、地图、首领、登录与设置。分别提交风格板、资源来源及适配清单、同机位实机前后对照、短录像、各分辨率截图与实际资源缺项检查。不得用成长流程、测试数量、单张概念图或只换颜色作为美术整改通过依据。现有资源按用途复用，缺失映射先修，缺少合格环境资源再补齐。所有建议尚待实现与实机验收。
