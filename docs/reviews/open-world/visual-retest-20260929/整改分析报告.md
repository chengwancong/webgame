# 《深渊行者》美术、游戏界面与交互整改分析报告

日期：2026-09-29。结论：**本轮整体未通过视觉验收。基础操作路径可运行，但尚未形成“色彩浓厚、厚实卡通、类似《魔兽世界》气质”的完整游戏画面。**

这次验收关注用户最在意的“看起来、操作起来是否像预期的游戏”。没有用成长通关、测试数量或构建成功替代美术判断。本轮只执行验收、记录证据和提出整改方案，没有修改游戏运行代码或素材。

## 1. 本轮检查了什么

- 只读检查当前常驻入口 `http://127.0.0.1:8612/` 的登录画面。
- 从当前源码重新构建客户端，在独立临时 PostgreSQL 和 API 下，通过真实页面创建测试角色，进入营地、野外与自动战斗，打开背包、构筑、目标、设置、远行和自动设置。
- 检查 1280×720、1600×900、1920×1080、1024×576 四种尺寸，测量面板和小地图边界。
- 检查打开面板暂停、Esc 返回、手动移动接管自动战斗和空格暂停。
- 核对实际素材、资源清单、渲染消费者、资源构建脚本和已有完成报告。

源码指纹：`5671b158aea05014df0080786353731185399ce9ae73743b611c359c8f8f7acf`，64 个文件。源码与 `public/art` 资源在本轮运行前后均未变化。原始数据和逐项素材哈希见 [result.json](result.json)。

浏览器：Chrome 无头模式、软件 WebGL。截图证明这次运行的实际输出；**不证明原生帧率、两小时稳定性、完整动画质量、声音听感或全部首领表现通过**。战斗采样时世界有 31 个存活敌人，不等于 31 个都在屏幕内。

## 3. 直观问题、原因和优先级

本报告中 P1 表示阻塞本轮目标画风或造成整改成果回退；P2 表示明确的界面、理解和使用问题。没有证据支持将本轮视觉问题列为数据损坏级 P0。

### P1-01：世界仍明显是几何原型，目标色彩没有进入实际地面

**证据：**[营地](02-camp.png)、[隐藏 HUD 的营地](03-camp-world-only.png)、[野外战斗](11-battle.png)。道路和草地均显示连续规则菱形；房屋缺少真实墙体、门窗、屋檐和材质；大面积空地没有形成场所。

**代码原因：**`apps/web/src/scene.ts:36` 附近仍采用 `baseTerrain=0x66775B`、`baseRoad=0xB3A181` 逐格绘制多边形。CSS 的 `--terrain`、`--road` 已改成浓郁色板，但不会自动改变 Phaser 的硬编码颜色。草地和石路纹理在 `preload()` 被加载，没有在当前地面绘制中使用。

**判断：**“纹理文件存在”“加载请求成功”和“世界已经使用该纹理”是三件不同的事。当前整改缺少最后一步，也缺少完整场景美术制作。

### P1-02：树木换了载体，造型质量没有达到要求

**证据：**[战斗画面](12-battle-later.png)和实际 `tree-sprite.png`。树木已通过图片精灵绘制，但树冠仍由几层近似椭圆叠加；体积、枝干结构和明暗分组有限。

**原因：**把 Graphics 几何图变成 PNG，并不会自动产生手绘材质或厚实奇幻造型。当前 96×120 图片的画面质量，不能由“精灵已接入”这一工程事实证明。

**整改要点：**重新做树形轮廓、主枝、树干根部、成组受光与冷色暗部，再处理尺寸和锚点。不要继续只加随机小点或提高饱和度。

### P1-03：角色、环境、HUD 和图标仍来自几套视觉语言

**证据：**角色有较细致的描边动画，环境是平面几何，HUD 是旧银灰金属框，系统入口是白色工具图标，技能是低分辨率彩色小图，新弓和星矛又是另一种简笔表现。[背包](05-bag.png)、[构筑](06-build.png)。

**原因：**逐项替换颜色和图片，没有先确定一屏组合场景里的形体、比例、材质、光照与清晰度关系。

**整改要点：**先完成一屏“营地出口—道路—林地战斗”的完整样板，再扩展地图和系统界面。当前角色可以用于样板，但必须与环境一起验证；若始终无法统一，再决定适配或替换，不能默认已有角色适合所有新画风。

### P1-04：旧边框仍在生效，UI 尚未形成统一的奇幻套件

**证据：**截图中的银灰横条和金属侧边仍很醒目。计算样式仍引用 `/art/ui/panel-frame.png`；上边框 26 px、左右边框 20 px。对应 `style.css:12`、`:50`、`:166`。

**原因：**底色 token 更新了，实际九宫格资源、切片和内容盒模型没有一起重做。

**整改要点：**制作同一套木石、古铜、皮革或雕刻材质的框架；HUD 用紧凑规格，背包等大窗用完整规格。厚实感通过角件、材质和明暗表现，不等于所有面板都增加粗边。

### P1-05：素材更新没有进入可复现的资源生产流程

**证据：**`tools/build_ui_assets.py:86` 起先删除整个 UI 输出目录；`SKILL_MAP` 没有 `lance`，`GEAR_MAP` 没有 `bow`；随后重新生成清单，并把这两个 ID 写回缺失列表。

**影响：**当前新增 PNG 和手改清单会在再次运行该脚本时被覆盖或删除，后续构建可能把已整改内容恢复成缺项。

**证据范围：**这是从清理操作、输入映射和清单输出静态核对得出的确定性风险。本轮没有在真实资源目录执行破坏性重建。

**整改要点：**建立唯一资源输入清单，收录旧素材导入与新制素材；先输出到独立暂存目录，校验 ID、文件、哈希和用途，再发布生成目录。禁止把只存在于生成目录中的文件作为唯一原稿。

### P2-01：六个面板标题实际为空

**证据：**六个对话框有正确的 `aria-label`，可见 `h2` 全部为空。

**原因：**`presentation.ts:261` 在 `title=''` 时就创建了 `head` 字符串，后续分支给 `title` 赋值不会改变已经生成的字符串，最后在 `:352` 插入旧 `head`。

**修法：**各分支先完成 `title`、`body`，再生成标题栏；或由统一面板渲染函数接受已经确定的标题。使用同一标题源绑定可见标题与无障碍名称。

**通过条件：**六个面板标题非空、名称一致；关闭再打开、切换背包标签后仍正确。源码中出现 `title='行囊'` 不能作为通过证据。

### P2-02：小地图越界比上轮更严重，修复漏算边框

**实测：**四种分辨率均外框宽 164 px、画布宽 150 px、左右边框各 20 px、左右内边距各 6 px。可用内容宽度仅 `164−40−12=112 px`，容不下 150 px 画布。

**结果：**画布越出外框右边 12 px，贴到视口右边；正文没有横向滚动条也不代表小地图未越界。

**修法：**边框先按新套件确定，再让画布服从真实内容宽度、保持正方形；若坚持 150 px 显示宽度，就必须给它足够的外框宽度。不要仅改一个宽度数字，也不要用 `overflow:hidden` 遮掉地图内容伪装修复。

**通过条件：**四种尺寸下，画布完整包含在内框中，四边安全距离正确，图例可读，标记不被裁切。

### P2-03：背包和构筑有功能结构，但视觉主次和图标清晰度不足

背包已有四个部位、格子、比较和操作，这些结构可以保留。问题是旧框过重、空格材质过亮、物品图混杂，角色装配存在感弱。新弓不再是剑，但缩入格子后显得细小，和其他装备的绘制精度不同。

构筑面板把十二个技能铺成相似卡片，说明、冷却、消耗、升级、排序争夺注意力；当前四技能方案没有成为主视觉。部分技能原图为 24×24，放大后明显模糊。应固定“当前装配与顺序”，下面浏览技能库，右侧或展开区显示选中技能详情；保存和未保存状态保持可见。

### P2-04：登录、地图入口和自动设置仍偏工具界面

登录页直接叠在测试营地上，缺少游戏主视觉和世界氛围。[登录](01-login.png)。远行页是文字区域按钮，尚未建立空间关系；自动设置是横向表单，缺少活动范围的直观预览。[自动设置](13-auto-settings.png)。

自动设置当前明确写着“拾取筛选与低生命停止尚未提供”；这是尚未实现的交互能力，不能记录为完整交付，也不应长期把研发说明展示给玩家。实施时需要补行为和状态反馈；在补齐前，报告应准确列为未完成。

### P2-05：战斗已有事件反馈，但还缺少成套表现

实际可见伤害数字、红色范围、护盾圈和地面掉落，基本反馈链成立。飞行物、范围和护盾仍主要是圆点与细线，未形成各技能的材质、节奏和强度差异。角色周围多个圈重叠时，友方效果、危险和自动范围的区别主要依赖颜色与线宽。

先制作六个切片技能的施放、轨迹或区域、命中、结束阶段；普通攻击保持短促，危险保留清晰边缘与时点；自动活动范围在设置或选中时强调，平时减弱。具体音效、全套动画和密集战斗下的可读性需要另外录制与实听，本次不标为通过。

## 4. 必须固定的美术方向

**核心要求：色彩浓厚、鲜明卡通、厚实奇幻，类似《魔兽世界》的美术气质。**

关键词：夸张比例、厚重轮廓、手绘材质、强明暗体积、暖冷对比、丰富区域色彩、史诗冒险、清晰战斗、游戏化界面。

英文关键词：`stylized high fantasy; rich saturated colors; chunky silhouettes; exaggerated proportions; hand-painted textures; strong value grouping; warm-cool contrast; epic adventure; readable combat; illustrated fantasy UI; Warcraft-inspired visual direction`。

“类似”落实到上述视觉原则与原创资源，不要求改变成三维游戏。保持二维斜视地图、角色左右朝向、脚底定位和纵向遮挡。

### 落到画面上的具体规则

1. **色彩：**林地使用浓郁绿、黄绿受光、暖赭石道路与局部蓝色魔法；遗迹以后再建立紫、冷石和橙火的区别。不要全屏同时提高饱和度，背景与主体仍要有层级。
2. **形体：**树冠分大块、树干有承重和根部；建筑有屋顶厚度、墙面转折、门窗凹陷；岩石有主要受光面和暗面。禁止用“多几个圆”替代这些结构。
3. **光照：**首批统一左上主光，暖亮部、偏冷暗部和接地阴影；角色、树木、掉落和建筑看起来位于同一个空间。
4. **材质：**草地、泥土、石块、木材各有可辨特征。优先大块明暗和边缘，纹理密度不能盖过角色、道路与危险。
5. **UI：**采用深蓝底和琥珀金强调，搭配原创古铜、木石或皮革套件；按钮、槽位、标题、图标的表现精度一致。避免旧银灰工具窗与新素材混搭。
6. **清晰度：**按实际显示尺寸检查，不能只展示放大的资源预览。低分辨率原图无法满足目标尺寸时，重新制作原稿，不以插值放大冒充细节。

上述 skills 是实施任务的选择建议，每项只加载相关内容。本轮实际使用 `frontend-design`、`ui-ux-pro-max` 做评审。当前是 Phaser 工程，不使用 Godot skill 的导出检查来证明这条路径通过；本轮也不需要数值平衡 skill 来替代视觉验收。

## 6. 工程上怎么避免再次“文档完成，游戏没变化”

### 6.1 明确修改的所有者

- 世界的主题和区域表现应有一份明确的配置源，由 `scene.ts` 消费；CSS 可以消费映射后的 UI token，但不能把 CSS 中未使用的颜色当作世界已改色。
- 素材以资源清单和可保留的原稿为来源；`public/art` 是输出，不应成为新素材唯一存储点。
- UI 可见标题、无障碍标题使用同一数据源，布局按实际边框计算，不另写一套假定值。
- 表现层消费战斗与奖励事件；调整动画、纹理和 UI 时，不改变伤害、结算、资产归属或存档规则。

### 6.2 每项素材必须走完同一条链

`用途与风格 → 原稿 → 导出 → 清单 → 加载 → 实际消费 → 实机场景 → 验收证据`。

每项登记：稳定 ID、原稿位置、来源/许可状态、尺寸、透明边、锚点、主光、显示尺度、消费者、哈希、截图位置、缺失或替代说明。对动画还需动作、帧率和事件时点。概念图只能证明方向；必须切分、适配、接入后才能算运行资源。

### 6.3 报告分开写三种状态

| 状态 | 能说明什么 | 不能推出什么 |
|---|---|---|
| 文件或代码已生成 | 产物存在 | 资源已被使用、画风达标 |
| 构建/运行检查通过 | 该路径技术上可运行 | 视觉质量、性能、玩法全部合格 |
| 现场视觉验收通过 | 指定版本、画面和范围符合标准 | 其他区域、其他分辨率或未来构建自动通过 |

当前 `art-final-acceptance.md` 中“地面替换”“面板标题已有”“小地图修复”“无几何占位”等结论应按本报告改为实际状态。“饱和度提升 30–50%”“性能无回退”缺少本轮可对应的测量依据，不能继续作为验收证据。

## 7. 推荐执行顺序与退出条件

### R0：先修确定性问题和资源回退风险

修标题生成顺序、小地图盒模型、资源构建映射和清单；更正完成报告。完成后用六个面板、四种尺寸和临时目录资源重建验证。

这一批只消除明确缺陷，不因此宣布美术整体通过。

### R1：完成一屏完整视觉样板

范围固定为“营地出口—一段道路—林地战斗空地—入口地标”。包含实际角色、至少两类敌人、树石建筑、六技能中的代表性效果、掉落和新 HUD。先确定资源组合与光照，再接入当前引擎。

退出条件：正常 HUD、隐藏 HUD、战斗中、掉落四种画面均呈现同一美术语言；导航与碰撞仍准确；没有用大背景图覆盖整个玩法空间。样板未过不批量扩区域。

### R2：将已通过的视觉套件扩展到系统界面

依次处理背包、构筑、目标/远行、自动设置、登录/设置；每个模块同时检查视觉、状态和输入。不得只替换 CSS 颜色就标记完成。

### R3：按同版本实机交付

交付四种尺寸截图、同场景前后对照、15–30 秒真实运行录像、资源清单、未完成列表及清理记录。动作与音效用正常浏览器实际检查，性能如有宣称必须另附明确设备与测量方法。

## 8. 下一轮如何算达标

以下是本项目建议采用的验收条件，应在下一轮记录中逐项给证据，不计算未经定义的“100% 美术完成度”。

1. 一屏实机能体现浓厚色彩、厚实轮廓、手绘材质和暖冷体积，角色、环境、图标和 HUD 风格协调。
2. 地面没有依赖明显交替明暗形成的测试棋盘；道路边缘、转角和地块边界连续。
3. 建筑、树木、地标不再是当前几何占位造型；隐藏 HUD 后仍有清楚场所和路线。
4. 新 HUD 与面板实际使用统一资源，旧银灰框已退出本批界面；标题可见。
5. 小地图在四种尺寸下完整包含于内容区；背包、构筑与设置关键操作可达。
6. 弓、剑、星矛等在游戏实际显示尺寸下能区分，绘制质量与同组图标相近。
7. 模式切换、输入接管、面板暂停、返回、处理等待、失败提示与实际行为一致。
8. 普通交战中能辨玩家、敌人、主要危险与掉落；录像展示施放和命中对应。密集压力场景单列验证。
9. 资源可以由保留的输入重新构建，新图不会在下一次执行脚本时消失。
10. 报告逐项引用同一源码与资源版本的证据，明确未测项；构建成功不代替视觉验收。

建议另安排未参与开发的人做一次简短理解检查：指出主角、危险、下一步目标、自动模式状态，以及选中装备相对当前装备的关键变化。记录实际回答，不把自动脚本当作玩家理解证据。
