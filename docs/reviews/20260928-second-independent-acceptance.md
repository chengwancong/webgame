## 未通过项

### 1. [P1] 回收旧检查目录时，先删除了仍在运行的数据库文件

位置：`tools/check.py:104`、`tools/runowner.py:61–98`。

启动检查时先调用：

```python
runowner.reap_stale('awr-check-*', OWNER_TOOL)
```

此调用没有 stopper。若上次检查的父进程已退出，而它启动的 PostgreSQL 仍运行，回收器会将整个父目录及内部数据库直接删除。后面的 `pgproc.reap_stale()` 已经找不到数据库目录，无法再按原方式停止该实例。

本轮用真实 PostgreSQL 验证，与 `check.py` 相同地登记父检查目录所有者、在内部建立数据库，再令辅助父进程退出。调用上述原回收函数后：

- 父检查目录被删除，记录 `removed=true`，删除约 40 MB。
- 数据库数据目录不存在。
- PostgreSQL 主进程仍存活，原端口仍在监听。

这是“删了目录但没有收尾资源”，不能算成功回收。本轮随后通过已记录并核对身份的自有 PostgreSQL 进程完成停止，未留下该测试库。

此外，`check.finish()` 第 139–146 行即使记录了数据库停止失败，仍继续删除整个目录；第 122、153、156 行的成功状态及退出码也不因 cleanup errors 改为失败。这是代码可直接确认的另一条同类风险路径。

**修复要求：**按资源依赖顺序先停止并确认所有子进程/数据库退出，再删除父目录。父目录回收器必须知道内部资源；停止失败时保留目录和所有权记录，返回明确失败。把清理错误纳入检查退出码和报告 `ok`。不要仅分别证明“数据库回收器有效”和“目录删除有效”，必须验证它们在真实检查入口中的调用顺序。

证据：`20260928-second-independent-evidence/lifecycle-probes.json` 的 `check_startup_parent_reap`。

### 2. [P2] 收到中断时，进程守卫删除日志目录却留下子进程

位置：`tools/processguard.py:187–191`，与 `tools/check.py` 的 SIGTERM → KeyboardInterrupt 路径相关。

`run_guarded()` 的最外层 finally 只调用 `rmtree`。正常超时会调用 terminate，但父检查收到 SIGTERM、发生 KeyboardInterrupt 时不走这个分支。子进程使用 `start_new_session=True`，因此不会自动跟随父进程退出。

本轮使用原 `run_guarded()` 启动一个真实 Python 子进程，并给包装父进程设置与检查入口相同的中断语义。发送 SIGTERM 后，父进程结束，但被管理的子进程仍存活。它随后由本轮按已记录的 PID 显式停止。

**修复要求：**在所有退出路径的 finally 中处理仍存活的自有子进程组：终止、限时等待、必要时强制结束并回收；确认退出后再删日志目录。增加运行中的外部中断回归，同时检查进程和文件系统，不能只验证 timeout 分支或临时目录是否消失。

证据：`lifecycle-probes.json` 的 `guard_interrupt`。

### 3. [P2] `make dev` 正常退出没有删除数据库，却输出“bytes removed”

位置：`tools/dev.py:95–100`、`tools/pgproc.py` 中 `stop_and_measure()`。

`stop_and_measure()` 的职责是停止并返回计量结果，本身不删除目录。`check.py` 后面会删除父目录，但 `dev.py` 没有对应步骤，只直接把统计到的数据库大小打印为已删除。

本轮完成默认 Web 操作后向开发进程发送其支持的 SIGTERM，命令正常返回 0：API 和静态服务端口已关闭，PostgreSQL 已停止；但是临时目录仍存在，实际剩余 **40,558,935 字节**。日志却输出：

```text
postgres (verified, 40558305 bytes removed)
```

这既不符合 README 的一次性删除约定，也使清理数字与实际状态不符。该目录已在本轮最终收尾中删除。

**修复要求：**停止确认后显式删除本次数据库工作目录，复查剩余字节，再输出实际删除量。若有删除失败，返回失败并保留可追溯记录。为 `make dev` 的正常退出、SIGTERM 和启动失败分别验证文件、进程与报告；不能只复用 `make check` 的清理测试。

证据：`dev-shutdown-result.json`、`make-dev.log`。

### 4. [P2] `make db` 在没有 PYTHONPATH 的终端中启动失败

位置：`tools/pgproc.py:26`、`Makefile` 的 db 目标。

新加入的 `from tools import runowner` 依赖仓库根目录在 Python 模块路径中，但 Makefile 仍按文件方式运行 `.venv/bin/python tools/pgproc.py`。该脚本没有像 `dev.py`、`migrate.py` 那样建立根目录导入路径。

独立执行等价于以下命令的检查：

```sh
env -u PYTHONPATH make db
```

结果为退出码 2：

```text
ModuleNotFoundError: No module named 'tools'
make: *** [db] Error 1
```

现有测试从已加入根路径的 Python 进程中 import pgproc，因此不能替代这条公开命令的验收。

**修复要求：**统一包方式入口，例如从仓库根运行 `python -m tools.pgproc`，或建立明确的脚本导入路径。用去除 PYTHONPATH 的终端验证 `make db` → `make migrate` → API，并验证停止后的清理。

证据：`make-db-clean-env.json`。

## 为什么 33 项通过还不能签收

- 孤儿数据库测试直接调用 `pgproc.reap_stale()`，没有复现 `check.main()` 先回收父检查目录的真实顺序。
- 中断测试只覆盖 timeout；异常向上传播时没有检查子进程是否还活着。
- 没有测试 `make dev` 正常退出后的目录状态。
- `make db` 的文件入口没有在干净模块路径下运行。

因此当前主要问题是资源生命周期验证未贯穿实际入口，而非测试数量不足。应针对这些已复现路径补验收，避免继续用局部函数的结果推断完整流程。

另需保持报告准确：`test_low_hp_last_enemy_repro_keeps_the_killing_tick` 的内容与上轮原始规格并不完全相同（位置、攻击参数、技能前摇等也变了），不宜称为“只改 max_hp 的原始复现”。本轮已另外用保留的原始 JSON 通过验证，因此这不阻碍战斗缺陷关闭，但建议将该原始规格纳入固定回归。
