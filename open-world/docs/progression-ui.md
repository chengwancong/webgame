# 养成界面与服务端展示契约

> 日期：2026-10-05　范围：open-world　状态：已完成阶段 3

养成窗口沿用奶白浅金 Token 与共享控件。费用、可执行状态、属性预览、天赋前置、盘面关系、声望档位与奖励由服务端提供；前端只选择、排版和提交现有操作。本次不改变成长费用、点数来源、解锁规则或持久存档结构。

## 通用交互

- 操作区直接展示按钮。第一个可执行的普通操作为主按钮，其他操作为次按钮；无可执行普通操作时，首个普通操作禁用并显示服务端原因。天赋重置始终位于次级区，使用共享确认框，确认时核对角色版本。
- `progression-run` 选择对应操作，再沿原报价及提交链路核对。禁用操作不请求预览；报价期间改变选择会取消原次提交。过期报价、待确认写入与连接阻塞均不能提交。
- “投入后”使用 `ui-stat--delta`，仅显示攻击、生命、防御的非零变化；无变化显示“角色属性不变”。技能效果的变化仍由服务端技能参数承担，不伪造角色属性差值。
- 页头资源来自当前模块所有操作的非零成本，在 `view.currencies` 中查询名称与持有量。天赋点取服务端 `summary` 的 `天赋点` 项，格式为“剩余/总数”。
- “总加成”打开共享浮层，Tab 留在浮层，Esc 关闭并返回触发按钮。底部全局加成条及常驻刷新按钮已移除；错误状态提供重新读取。
- 分类页签使用已有 `tabsHtml({orientation:'vertical'})`。共享方向观察器在 ≤760px 时同步横排及 ARIA 方向；桌面使用上下键，窄屏使用左右键，保留 Home/End。提示点只消费服务端 `operation.enabled`。

## 可选字段

`progressionItemSchema` 与嵌套对象继续采用 `.strict()`；以下字段全部可选。它们是服务端生成的展示数据，不需要写入角色存档。

| 字段 | 含义与来源 |
| --- | --- |
| `state` | `learned / available / locked`；服务端根据保存进度和操作报价决定 |
| `rank / max` | 已投入等级或阶段、上限；天赋、雕文、突破觉醒、声望使用 |
| `tier` | 天赋层数；专精条目为 0，节点沿用内容表层数 |
| `requires` | 巅峰节点的前置节点 ID，直接来自内容表 |
| `effects` | `{stat,label,value}`；服务端提供玩家名称和展示单位。百分比效果已换算为百分点，例：攻击增幅（%）=2；射击数量等使用原数量 |
| `x / y / board / socket` | 巅峰盘内容坐标、盘编号、是否为雕文插槽；`board` 从 0 开始 |
| `slottedGlyph` | `{id,name,rank}`，实际已镶嵌雕文，未镶嵌时缺省 |
| `radius` | 服务端解析的雕文半径，与实际加成共用 `glyphRadius` |
| `stages` | `{id,label,state}[]`，服务端生成阶段轨道，前端不推断下一阶段是否开放 |
| `currentValue / nextValue` | 当前声望与下一档目标；最高档 `nextValue=null` |
| `progressRatio` | 服务端提供的声望进度比例，范围 0–1 |
| `rewardTiers` | 声望各档名称、门槛、状态和 `{name,value}` 奖励清单；金币与碎片数值与实际发奖共用 `reputationRewards` |

`summary` 中的加成名称由服务端提供：武器攻击加成、方阵攻击倍率、武器技能伤害加成、方阵技能伤害倍率、天赋点、巅峰点。天赋点额度仍受既有 60 点上限限制。

## 模块与回退

| 模块 | 当前布局 | 缺字段时的行为 |
| --- | --- | --- |
| 三系天赋 | 专精入口 + 按层排列、每层五列的树；单节点的最高层占整行 | 任一条目的层数或状态缺失，或天赋节点缺少等级、上限、效果时，回退原列表 |
| 巅峰盘 | 每盘独立节点连线，实际雕文显示在插槽内；跨盘关系显示连接名称 | 缺坐标、盘编号、前置关系或状态时回退列表 |
| 雕文 | 卡片网格，显示等级、半径和对应盘 | 缺等级、上限、状态、盘编号或半径时回退列表 |
| 角色突破/觉醒 | 阶段轨道与原服务端成本报价 | 缺等级、上限或阶段数组时回退列表 |
| 技能觉醒 | 永久分支轨道，显示服务端保存的分支名称 | 缺等级、上限或阶段数组时回退列表 |
| 区域声望 | 每区域进度条和档位奖励 | 缺等级、上限、当前/下一档、比例或奖励清单时回退列表 |

原天赋内容最高层有五个节点，因此仍按五列展示；只有内容提供“最高层单节点”时才使用整行关键节点布局。剧情入口继续调用 `story-gates.ts`，没有为验收关闭剧情校验。

## 共享组件变体

外观定义在 `apps/web/src/ui/controls.css`，页面 CSS 只负责排版、滚动、连线与 Token 引用，不覆盖 `.ui-*` 的颜色、字号、字重或 display。

- `ui-stat--delta`：已有差值比较组件。
- `ui-stat--effect`：天赋效果数值使用 H2 字号。
- `ui-progression-node`：固定占位的状态节点，选中不改变边框厚度和内边距。
- `ui-progression-node--specialization`、`--card`、`--track`：专精、雕文卡片、阶段与声望卡片变体。
- `ui-stage-track`：服务端阶段数组的展示。
- `meter.neutral`：共享中性进度条，填充和文字来自 Token。
- 页签提示点使用 `data-actionable=true`，方向使用既有 `data-tabs-orientation=vertical` 与 `--tabs-direction`。

## 验收与边界

类型检查、Vitest、浏览器验收按顺序执行。真实 Chrome 连接 `http://127.0.0.1:8612/`，通过现有登录、角色恢复、服务端报价、命令和数据库结果验证。测试只向专门创建的 `growth_ui_*` / `growth_legacy_*` QA 角色注入阶段初始状态，不修改已有玩家角色。

缺字段回退通过真实服务响应的只读删字段夹具验证，不发写命令；它验证旧响应兼容性，不伪称旧服务器已部署。保存进度的兼容性另用旧存档形状的 QA 角色核对。

各阶段证据保存在 [验收目录](reviews/progression-ui-20261005/)。每份 JSON 记录视口、面板边界、内部溢出、服务版本和实际操作；PNG 用于视觉复核。验收脚本为 `tools/verify-progression-ui-redesign.mjs`，复验前需要独立 QA 账号的 `.qa/progression-ui/session.json` 与 `character.json`，禁止用普通玩家账号替代。

提交保存于 `codex/progression-ui-20261005` 审阅分支，当前工作分支与暂存区没有切换。分支首先记录本次开始时相关文件的已有工作作为审阅基线，其后记录通用改造/天赋树及每个专属模块的独立提交；该审阅基线不是本次新实现，也不包含整个工作区的其他未提交依赖。审阅分支用于检查本次文件差异，独立检出运行需要当前工程的其他既有修改。


最终验证：`npx tsc --noEmit -p .` 通过；6 个 Vitest 文件共 53 项测试通过；`node tools/build-ui-tokens.mjs --check` 通过（288 个 Token）；Windows 托管服务保持 Running、当前用户 Limited 权限，8612 网页与 health 均返回 200。最终实机同时核对 health、content、网页客户端的 protocol/rules/assets 一致。

第二个独立 `growth_legacy_*` 角色使用缺少 version 和集合字段的旧 progression 形状恢复。实际核对保留金币 12345、强化石 321、矿石 37、已投入天赋与武器等级 7；新展示元数据由服务端补出。它是受控旧存档夹具，不是修改普通玩家的历史存档。
