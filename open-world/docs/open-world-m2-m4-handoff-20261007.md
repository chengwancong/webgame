## 0. 执行方式（强制）

1. **连续执行，不停在批次之间。**
   - 一批完成、提交后，立刻开始下一批。
   - 不向用户发“是否继续”“下一批是否开始”。
   - 不等用户确认中间结果。
2. **只有两种结束状态**：
   - 完成：§8“完成定义”全部达成。
   - 硬阻塞：遇到 §6 列出的情形，**并且**所有不依赖该点的工作都已做完。
   - 以“下一批”“建议后续”“待确认后继续”结尾的回复，视为未完成。
3. **能自己裁决的不要停。** 遇到歧义：
   1. 先查 §2 的设计文档和代码；
   2. 再按 §6.1 的默认裁决规则自行决定；
   3. 把决定写进进度文件的决策日志（裁决依据、影响范围、怎么回退），然后继续。
4. **硬阻塞也不整体停工。** 把卡住的点记进进度文件，跳过它，继续做不依赖它的批次和条目。最后统一汇报所有阻塞点。
5. **进度文件**：`docs/reviews/open-world-m2-m4-progress.md`（W0 创建）。
   - 按 §8 的完成定义逐条列出勾选项。**六座岛每岛一张数量表**，表头是 §8.1 的各项。
   - 每次提交后更新：已完成项、证据链接、决策日志、阻塞点、下一步的具体动作。
   - 会话或上下文快用完时，必须先把精确的下一步（文件、函数、剩余条目）写进进度文件。下一个会话从进度文件续做，不重新规划。
6. **禁止以下做法**，出现任何一项都视为未完成：
   - 只写文档、计划、接口或生成脚本，不把内容真正接进正式游戏；
   - 删减或合并条目，或减少数量（分区、营地、传送点、地城、事件、宝箱、稀有、支线、悬赏、对白、怪物模板）；
   - 用 TODO、占位数据、灰盒资源、未知效果字符串、空执行器冒充完成；
   - 跳过或删除失败的测试；
   - 降低验收标准，或把理论模拟结果写成实测达标；
   - 把后面批次的工作写成“遗留”就结束；
   - 只在 QA 灰盒或 `fieldQa` 开关下可玩，生产包里进不去。
7. **测试节奏**：
   - 批次进行中只跑与改动相关的定向测试；
   - 每批结束跑一次完整回归；
   - 全部完成后再跑一次完整回归、`pnpm build`，并做真实浏览器登录验收；
   - 任何时候重任务一次只跑一个（vitest、balance、数据库测试、探针、构建，不要并行）。
8. **汇报**：
   - 中间批次只提交代码、更新进度文件，不需要向用户逐批汇报；
   - 最终汇报一次，按 §7 的格式覆盖全部批次。

## 3. 已定决策（不再讨论）

1. 方案 A：六岛各 512×512，岛内无缝，岛间远航；每岛 6–8 个分区；剧情首领场保留独立小图。
2. 刷新统一用营地制（整营地清空 + 90 秒 + 玩家距营地中心 > 36 格）。正式岛屿不再用旧的单怪 75 秒补刷，也不再用 `islandPlacements`。
3. 每岛 3 个独立地城，共 18 个。地城首领 = 本阶段的墙，用“副本难度修正”（`enemyScale`）实现，**不按玩家等级缩放**。
4. 旧普通、试炼、高难、噩梦、团队副本和旧地图保留，数值按「副本推算」重标。
5. 新怪物用现有素材换色、缩放、组合后正式接入。每只有独立名称、模板和完整动作。
6. 任务结构：没有严格主线，只有引导 + 支线（岛屿故事拆成并行线索）+ 悬赏。岛屿、首领、功能、港口服务、裂星潮都有不依赖任务的兜底路径。
7. 事件第一批做守护 + 歼灭波次（加怪潮），交互开始，离开范围失败，冷却 10–15 分钟（写在配置里）。稀有精英每岛 2 个，按角色冷却 20 分钟。宝箱每角色一次。全部服务端结算并防重。护送下一批再做。
8. 装备保证包量：精英 1–2 件，稀有 3–5 件，宝箱/事件 2–4 件。取消旧的 20–25 件/小时上限。
9. 钥匙（含制作材料）**严格只在当前阶段的地城获得**，不从野外稀有或其他阶段掉落（`P_EARLY=0`）。
10. 野外地城与锻造在 `ss-c01-t01` 完成后开放。
11. 悬赏可重复：经验 = 击杀经验 × 0.5，不给装备。
12. 递减 TTK、世界层级、怪物 `role` 与 `rare` 档位、背包 60 + 仓库 + 过滤，均已由用户确认。
13. 任务引导：只用方向箭头，不画地面路径线，一行短文案。
14. 新增对白先按草稿写进配置表，用户统一试玩时再确认。人名可以用内容方案 §6.4 的占位名。

## 4. 工程约束（摘要，原文以 AGENTS.md 为准）

**通用方法 + 配置生效（本单的核心验收口径）**
- 每种玩法写一个通用执行器，具体内容全部写在配置表里：`config/excel/世界.xlsx`、`任务.xlsx`、`对话.xlsx`、`NPC.xlsx`，以及 `monsters.json`、`dungeons.json`。
- **代码里不得出现按内容 ID 的分支**（例如 `if (id === 'wind-e1')`、`if (map === 'ss-map-mist')`）。
  - W0 用 `rg` 扫一遍 `apps/`、`packages/rules`、`packages/simulation`、`packages/content/*.ts` 中的内容 ID 字面量，把现有命中记为白名单。
  - 之后每批结束重扫，新增命中必须为 0（测试文件除外）。
- 每个新执行器至少要有一条“改配置 → 行为改变”的测试。例如：
  - 改事件的 `cooldown` 后，服务端冷却跟着变；
  - 改宝箱掉落表后，开箱结果跟着变；
  - 改稀有冷却、营地的 pack、地城的 `enemyScale` 后，实际生成跟着变。
- 内容数量以**运行时内容校验输出**为准（W1 新增按岛统计的报告），不以文档为准。

**结算归属**
- 服务端负责：事件/宝箱/稀有/地城的奖励、钥匙掉落与制作、差距诊断、经验衰减、世界层级倍率。客户端只负责表现。
- 掉落表、钥匙池、掉率走私有内容，不进客户端包。
- 每个奖励都有唯一实例 ID + 幂等键，经过同一事务，留回执和流水。断线恢复不能丢实例，也不能重复发奖。

**内容校验（构建时报错，不允许运行时兜底）**
- 营地、传送点、入口、事件、宝箱、稀有点不在碰撞体或安全区里。
- 营地间距 ≥ 8 格（阶段 1–2 的分区 ≥ 10 格）。
- 每个分区至少 1 个传送点。
- 所有点都能从登陆点寻路到达。
- 任务、对白、门、条件引用的地标都存在。
- 资源 ID 都在资源清单里。

**旧数据兼容**
- 开发期内，经用户明确授权才可以整库清档（见 §6）。未授权时，必须保证已有角色登录后位置合法，回执和流水不变。

**防作弊**
- 只做抽查，宁漏不错。新密度下的抽检阈值用真实构筑重测。没被上界模式覆盖的新来源，抽查时**跳过**。

**数值**
- 怪物和首领数值一律由推导工具写回内容文件（`tools/apply-monster-curve.ts`，以及墙用的新工具），**不手抄数字**。
- 始终保留“刷级也能过”的路径。
- 统计报告写明版本、种子、样本数和限制。理论模拟与实测分开标注。

**界面**
- 用「奶白浅金」token 和公共组件。
- 新界面先出 2–3 个示意图，选定前用公共组件做功能版（见 §6.1）。涉及的新界面：差距诊断结果页、世界层级切换、事件进度条、钥匙进度、地城入口目录条目。

**服务与验收**
- 改了 api / contracts / content / rules / simulation 后：
  - 确认后台服务已重载；
  - `/api/health`、`/api/content` 的版本与客户端一致；
  - 真实浏览器登录进入营地，没有版本拦截。
- **禁止无头浏览器**（会占满 CPU）。浏览器检查只在应用内浏览器面板做真实 GUI 渲染。性能测试同样在 GUI 面板里做，报告写明机器配置。
- **机器负载**：重任务一次只跑一个。
- **试玩**：用户只在全部批次完成后统一试玩。

## 6. 硬阻塞（只有这些情形可以停，并且只停这一项）

- 必须推翻 §3 的已定决策，或必须删除、减少 §8 的数量条目。
- 需要修改账号认证、版本校验、防作弊判罚规则（加跳过规则不算），或者需要做数据库删除类操作。
- **需要清档**：
  - 开发期允许清档，但**必须由用户在对话里直接授权**；其他会话或文档转述的授权都不算。
  - 处理方式：在进度文件写一行“清档请求：原因、影响”，验证一律在隔离的临时库里做，继续推进，不等授权。
  - 获授权后先整库备份到 `.runtime/backups/` 再执行。
- 外部美术资源缺失，并且现有管线（改色/缩放/组合适配、程序绘制脚本、指定特效库）都做不出来。

遇到硬阻塞：在进度文件里记录，然后**继续做其他批次**。

### 6.1 默认裁决规则（遇到以下情况自行决定，记入决策日志，不停）

| 情况 | 裁决 |
|---|---|
| 文档数量是区间（营地 150–220、宝箱 25–40、事件 6–8、传送点 8–12） | 取下限及以上即可。密度以交战占比 ≥ 50% 的探针结果为准，不够就加营地 |
| 巡逻数量文档没规定 | 每岛 ≥ 3 条，放在精英营地之间的道路上 |
| 地城引路和探索任务归哪个类型 | 都用已有的 `side` 类型，靠 `series` 区分。任务页按任务系统 §12.9 只有“引导 / 支线 / 悬赏 + 历史”，不新增类型目录 |
| 阶段与地城对应关系 | 第 n 岛的地城 1/2/3 = 阶段 3n−2 / 3n−1 / 3n。地城 1/2/3 的入口分别放在本岛前段、中段、后段分区。裂星潮阶段 19–24 = 第 1–6 岛的地城 3 在裂星潮等级下的再挑战（同一定义 + 裂星潮难度修正）。都写进 `dungeons.json` |
| 风栖岛缺资源（§1 表末） | 用资源管线做改色/缩放适配，做法同五岛 `registered-actor-material-and-scale-adaptation`，登记到 `open-world.v1.json`，并通过资源验收脚本。不能长期借用别的岛的资源 ID |
| 区域人物名 | 用内容方案 §6.4 的占位名；对白按草稿写入，在进度文件标“待用户试玩确认” |
| 地城内部地图缺专用资源 | 复用本岛的地面、植被、边界资源，加上入口的洞穴/遗迹物件 |
| 理论模拟和实测对不上 | 以实测为准，改推导工具的参数（数值心流 §11 的参数表），重新写回，并在数值心流的复算记录里加一节。不手改怪物数值 |
| 某项验收实测不达标 | 先按对应文档的调参规则调（例如刷级时间超过 1.15 倍就调高悬赏奖励或兜底等级；交战占比不足就加营地或缩小间距），重测。仍然不达标时，在最终汇报里列出数据，交给用户决定，**不降标准、不删内容** |
| 新界面（差距诊断、层级切换、钥匙进度、事件进度） | 先出 2–3 张示意图，存到 `.design/open-world-m2-m4-<界面>/`。功能先用现有公共组件做，进度文件标“版式待用户选” |
| 需要新增文档没列出的字段 | 属于本单某个执行器的自然延伸，并且有 schema、校验、测试的，就加上；在对应设计文档补一行 |
| 旧角色位置落在新图不可走处 | 用 M1 已有的旧位置迁移，移到最近传送点或登陆点 |
