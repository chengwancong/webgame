## 0. 执行方式（强制）

1. **连续执行，不停在批次之间。**
   - 一批完成、提交后，立刻开始下一批。
   - 不向用户发“是否继续”“下一批是否开始”。
   - 不等用户确认中间结果。
2. **只有两种结束状态**：
   - 完成：§7“完成定义”全部达成。
   - 硬阻塞：遇到 §5 列出的情形，**并且**所有不依赖该点的工作都已做完。
   - 以“下一批”“建议后续”“待确认后继续”结尾的回复，视为未完成。
3. **能自己裁决的不要停。** 遇到歧义：
   1. 先查三份设计文档和代码；
   2. 再按 §5.1 的默认裁决规则自行决定；
   3. 把决定写进进度文件的决策日志（裁决依据、影响范围、怎么回退），然后继续。
4. **硬阻塞也不整体停工。** 把卡住的点记进进度文件，跳过它，继续做不依赖它的批次和条目。最后统一汇报所有阻塞点。
5. **进度文件**：`docs/reviews/build-variety-progress.md`。
   - 按 §7 的完成定义逐条列出勾选项。
   - 每次提交后更新：已完成项、证据链接、决策日志、阻塞点、下一步的具体动作。
   - 会话或上下文快用完时，必须先把精确的下一步（文件、函数、剩余条目）写进进度文件。下一个会话从进度文件续做，不重新规划。
6. **禁止以下做法**，出现任何一项都视为未完成：
   - 只写文档、计划或接口，不实现；
   - 删减或合并条目，或减少数量（技能、原子、威能、潮印、套装）；
   - 用 TODO、占位数据、未知效果字符串、空执行器冒充完成；
   - 跳过或删除失败的测试；
   - 降低验收标准；
   - 把后面批次的工作写成“遗留”就结束。
7. **测试节奏**：
   - 批次进行中只跑与改动相关的定向测试；
   - 每批结束跑一次完整回归；
   - 全部完成后再跑一次完整回归、`pnpm build`，并做真实浏览器登录验收；
   - 任何时候重任务一次只跑一个。
8. **汇报**：
   - 中间批次只提交代码、更新进度文件，不需要向用户逐批汇报；
   - 最终汇报一次，按 §6 的格式覆盖全部批次。

## 3. 工程约束（摘要，原文以 AGENTS.md 为准）

**结算归属**
- 服务端解析全部属性、套装、威能、潮印，产出结果参数。客户端战斗只执行，不重算成长公式。
- 持久状态（装备实例、法典、钱包、回执）只由服务端改。潮印只在局内生效，不进存档。

**新机制与内容**
- 新机制 = 唯一执行器 + 共享 schema + 定向测试。**禁止未知效果字符串。**现存的守护者 `special:'damage_reduction:0.1'` 就是反例（需求 A.11-1），R4 改成数据。

**旧数据兼容**
- 保留账号、角色、装备实例、奖励回执和流水。
- 规则变更用版本切换：旧装备旧规则可读，新掉落用新规则。

**防作弊**
- 只做抽查，宁漏不错。
- 新触发或新动作没被上界模式覆盖时，抽查**跳过**，不判违规。

**数值**
